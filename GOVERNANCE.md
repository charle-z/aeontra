# Governance

Aeontra currently uses a primary-maintainer model. The project is not governed by a
foundation, company, token, or paid membership program.

## Decision making

The primary maintainer is responsible for releases, security response, repository
administration, and the final decision when consensus cannot be reached. Design and
behavior changes should still be discussed through focused issues and pull requests so
the rationale remains reviewable.

Decisions prioritize:

1. explicit and bounded authority;
2. isolation, revalidation, auditability, and recovery;
3. useful agent capability;
4. compatibility and operational simplicity;
5. evidence from real users and measured workloads.

Security-sensitive reports use the private process in `SECURITY.md`, not public design
discussion.

## Roles

- **Contributor:** submits issues, documentation, tests, or code.
- **Trusted contributor:** has a record of accurate, scoped contributions and may help
  reproduce or review changes.
- **Reviewer or triager:** helps classify issues and review areas where they have
  demonstrated context.
- **Maintainer:** may merge, release, administer security-sensitive settings, and accept
  responsibility for the project's authority model.

Roles are based on trust, judgment, sustained participation, and the needs of the
project. A number of commits or elapsed time does not guarantee promotion.

## Changes to governance

Material governance changes should be proposed publicly and documented in this file.
Security response details, credentials, private infrastructure, and personal maintainer
memory remain private.

Enterprise governance, commercial licensing, billing, and multi-tenant administration
are deferred until real adoption produces measured requirements.
