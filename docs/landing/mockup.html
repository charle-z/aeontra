MCP DEVBOX — SECURE AGENT FIRMWARE Hosted on CubePath · rev cfbf1d4 · 102 tools

An AI agent that builds and ships real software on my own infrastructure — without a free shell.

MCP Devbox turns a ChatGPT subscription I already pay for into an agent that works on real repositories: read, patch, run tests, create repos, deploy. No API costs. The agent gets capability, not custody of the machine.

It exists because ChatGPT Plus and Codex have limits — different limits — and both run in environments I do not control. Paired with Coolify on CubePath I get control, persistent memory and my own rules. It has since grown an Edge that operates safely on my own WSL machine.

Most of this codebase was written by the agent through its own MCP surface, much of it from the ChatGPT mobile app, in sessions of roughly 102 minutes. The project deploys, validates and signs its own releases.

01 · AUTHORITY MODEL

THE DIFFERENCE IS AUTHORITY, NOT ACCESS

Handing an agent a terminal is easy, and most projects do exactly that. This is the harder version:

  • Directory jail that also covers command execution, not only file reads
  • Secret denial by path and content, with output redaction and canary tests
  • Closed allowlist of commands — no free shell exists to call
  • Writes are patch-first, validated before they apply
  • Consequential actions need a cryptographically named, expiring, single-use plan plus owner approval, revalidated at execution
  • Everything is audited; credentials are used, never returned to a model turn

Nothing here is a runtime toggle. The absent capabilities were never built, so there is nothing to misconfigure.

WHY THE EDGE MATTERS

The Edge connects outbound only: no inbound port is ever opened on my machine. It runs as a dedicated non-root user inside Bubblewrap, with roots exposed as aliases so the server can never send an arbitrary path. Privileged effects go through a closed helper profile — never sudo with a model-supplied command.

SELF-HOSTABLE

This is single-owner infrastructure by design, so instead of a shared demo tenancy the whole thing is self-hostable: bring your own Coolify instance and connect your own client. See the repository and its deploy and connect guides.

04 · HOST & ADMISSION

SQUEEZING A MICRO VPS, HONESTLY

The control plane runs on a 2 vCPU / 3.8 GiB KVM guest. Rather than guess, the host was profiled at rest and during a real no-cache Coolify redeploy with bounded probes (mpstat, iostat, pidstat, sar, /proc/pressure). The interpretation is committed as dated evidence in the repository.

DIMENSIONIDLEUNDER BUILD

host memory peak—2.33 GiB, no OOM

no-cache redeploy—~133 s sustained

The finding overturned the intuitive answer: memory was never the bottleneck. CPU is. A single no-cache build saturates the box, so admission control has to be arithmetic rather than optimism:

capacity 2 vCPU = 2.00 vCPU-s / s baseline idle control plane, p95 ≈ 0.82 vCPU (41%) build job one no-cache image build, p95 ≈ 1.88 vCPU (94%) headroom 2.00 − 0.82 = 1.18 vCPU available verdict → 1.88 > 1.18  —  at most ONE build-class job may be admitted, and it must not share the window with another.

So the scheduler being built (P16) treats CPU as the primary admitted dimension, keeps separate VPS and Edge execution pools — heavy work belongs on the Edge, which has its own capacity and its own authority — and adds durable queueing, fairness and deduplication so that any number of chats can ask for expensive work without starving the control plane. Memory, I/O and network stay enforced, just not pretended to be the current limit.

Honest status: the numbers above are a measured planning baseline. Final worker calibration and queue enforcement are in progress, not claimed as finished.

05 · EVIDENCE

WHAT IT LOOKS LIKE WHEN THINGS GO WRONG

The interesting part of an autonomous pipeline is not the successes, it is what happens when a gate says no. These are real, checkable moments from the project's own dated evidence and history — not a rehearsed demo:

Every phase is sealed with dated evidence and green remote gates, or it is not sealed at all. A gate that can be talked out of failing is not a gate. The record lives in the repository under docs/baselines/, next to the specs and threat models that authorized each change.

The loop is the product: the scanner reports, the agent reads the actual log, maps it to a concrete cause, proposes a bounded fix, revalidates the full suite, and only then may the gate go green. When the fix was not available — a private repository that could not run GitHub code scanning — the agent refused to publish the repository or disable the check, and swapped in an equivalent scanner instead.

Standing gates across both projects: CodeQL, staticcheck, govulncheck, Grype, Trivy, Syft/CycloneDX SBOM, Gitleaks full-history, dependency and lockfile audits, the Go race detector and bounded fuzzing — all blocking, all pinned by commit SHA.

08 · HONEST LIMITS

WHAT THIS IS NOT

  • Universal OS isolation and egress control are not finished. Hard isolation is Linux-only; on Windows it runs under WSL2
  • Single-owner. There is no multi-tenancy, and adding it hastily would weaken the authority model that gives the project its value
  • A stolen owner credential is still a stolen owner credential. Narrow authority shrinks the blast radius; it does not abolish trust
  • The durable autonomous mode needs its own model credential. A chat subscription cannot be turned into an unattended agent by wishing
  • Queue enforcement and final scheduler calibration are in progress, measured but not yet complete
  • Not a general-purpose terminal, and deliberately never will be
